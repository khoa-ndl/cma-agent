# Spec: CMA Agent

**Owner:** Khoa Nguyen, Nguyen Design Labs
**Date:** 2026-10-10
**Status:** Approved
**Source:** [intent.md](intent.md)

This document defines what CMA Agent does, the data it stores, the screens it presents, and how each requirement is verified. Release 1 is specified in full; Release 2 is outlined and will be detailed before its build begins.

## 1. Decisions

| Area | Decision | Rationale |
|---|---|---|
| Application framework | Next.js (App Router, TypeScript) | One codebase for UI and server logic; native fit for Vercel |
| Hosting | Vercel | Zero-config deploys and preview URLs per branch; no Vercel-only APIs, so the app also runs on any Node.js host |
| Database | Neon (serverless Postgres), connected through the Vercel Marketplace integration | Free tier scales to zero when idle and resumes automatically on the next query, so the application is never paused; standard Postgres keeps the schema portable |
| Database access and migrations | Drizzle ORM, with versioned SQL migrations committed to the repository | Typed queries; migrations run unchanged on any Postgres host |
| AI model | Claude Sonnet 5.5 (`claude-sonnet-5-5`) via the Anthropic TypeScript SDK | Strong tool use and reasoning at half the cost of Opus 5.5; model is a single configuration value |
| Comp selection and adjustments | Hybrid: deterministic code computes; the model selects and explains | Figures are repeatable and auditable; the model contributes judgment and narrative |
| Subject property input | Address autocomplete with pre-filled, editable facts | Fast demo path while still showing how adjustments respond to property facts |
| PDF generation | `@react-pdf/renderer`, server-side | Lightweight, runs in serverless functions, no headless browser |
| Credits | Fixed per action: report = 5 credits, chat message = 1 credit | Predictable for users; cost variance absorbed by the operator |
| Default allocation | 45 credits (5 reports + 20 chat messages) | Matches intent.md |
| Access code storage | Postgres table (Release 1) | Balances persist across serverless invocations; carries forward to Release 2 |
| Release 2 authentication | Better Auth (open-source library) | Stores users in the project's own Postgres tables, so accounts move with the database; no vendor-hosted user store |
| Sample dataset | ~10 areas, ~1,500 records, generated by a seeded script | Sufficient comp density; reproducible |

## 2. Architecture

```
Browser (Next.js pages)
   │  access code (HTTP-only session cookie)
   ▼
Next.js route handlers (server only)
   ├── Credits service ── Neon Postgres: access_codes, credit_ledger, reports
   ├── CMA agent loop ── Anthropic API (Claude Sonnet 5.5)
   │      └── tools ── Analysis engine (deterministic TypeScript)
   │                     └── DataProvider interface
   │                            └── SampleDataProvider ── Neon Postgres: property
   └── PDF renderer (@react-pdf/renderer)
```

- **The API key and database connection string exist only on the server.** The browser never calls Anthropic or connects to the database directly.
- **Database access** goes through Drizzle and a single connection module. In the sandbox deployment it uses Neon's serverless Postgres driver, which is designed for short-lived serverless functions.
- **Progress streaming:** the run endpoint returns a server-sent event (SSE) stream. Each agent step (tool call started, tool result summarized, reasoning note, final result) is emitted as an event and rendered in the UI as it arrives.
- **DataProvider interface:** the analysis engine and agent depend only on this interface. Release 1 ships `SampleDataProvider`; a future `ResoWebApiProvider` implements the same interface against an MLS feed.

```ts
interface DataProvider {
  searchAddresses(query: string, limit: number): Promise<AddressMatch[]>;
  getProperty(listingKey: string): Promise<Property | null>;
  searchListings(criteria: ListingCriteria): Promise<Property[]>;
}
```

### 2.1 Portability and swappable services

CMA Agent is a sandbox deployment of an architecture intended for client production systems. Each external service sits behind a single module, so a client deployment can substitute the services its IT department requires without changes to the agent, the analysis engine or the user interface.

| Service | Sandbox implementation | Swap point | Typical client substitutes |
|---|---|---|---|
| Property data | `SampleDataProvider` | `DataProvider` interface | RESO Web API (MLS feed), commercial property-data APIs |
| Database | Neon Postgres | `DATABASE_URL` and the connection module | AWS RDS or Aurora, Azure Database for PostgreSQL, Google Cloud SQL, Supabase, self-hosted Postgres |
| AI model | Anthropic API, Claude Sonnet 5.5 | Model client module and model configuration | Claude on Amazon Bedrock, Google Vertex AI or Microsoft Foundry; a different Claude model |
| Authentication (Release 2) | Better Auth with email links | Auth module | Client single sign-on (SAML/OIDC, e.g. Microsoft Entra ID, Okta) through Better Auth providers |
| Email (Release 2) | Resend | `EmailSender` module | Amazon SES, SendGrid, the client's SMTP service |
| Hosting | Vercel | Standard Next.js Node.js build | Any Node.js host or container platform (AWS, Azure, Google Cloud, on-premises) |

**Rules:**
1. **Standard interfaces only.** Database code uses standard Postgres features. No vendor-specific extensions, hosted auth stores or platform-only APIs.
2. **One module per service.** Application code imports the service module, never the vendor SDK directly. Vendor-specific code stays inside that module.
3. **Configuration through environment variables.** Switching a service is a change of environment variables and, at most, the one module that wraps it.
4. **Schema changes as code.** Every database change is a versioned migration in the repository, applied the same way on every host.
5. **Data moves with standard tools.** Postgres data transfers between hosts with `pg_dump` and `pg_restore`.
6. **One implementation until a second is needed.** A swap point is a module boundary, not a plugin system. Alternative implementations are built when a client requires them, not in advance.

### 3.2 Sample dataset

- **Areas (10):** Ballard, Capitol Hill, Fremont, Queen Anne, West Seattle (Seattle); Bellevue, Kirkland, Redmond, Issaquah, Shoreline.
- **Volume:** ~1,300 `Closed` sales with close dates in the trailing 12 months, ~200 `Active`/`Pending` listings.
- **Pricing model:** each area has a base price per square foot, sub-type mix and typical property profile. Prices combine the base rate, feature contributions, a monthly market trend and random variation. Parameters are documented in the generator.
- **Reproducibility:** a seeded generator script produces identical output on every run. The output is committed as seed data and loaded into the database by a seed script.
- **Labeling:** addresses are synthetic. Every record and every report is labeled "Sample data, not real listings."

### 3.3 Application tables

| Table | Purpose | Key fields |
|---|---|---|
| `access_codes` | One row per issued code | `id`, `code_hash`, `label` (operator note, e.g. recipient name), `credits_balance`, `revoked_at`, `created_at` |
| `credit_ledger` | Audit trail of every balance change | `id`, `access_code_id`, `delta`, `reason` (`grant`, `report`, `refund`, `chat`), `report_id`, `created_at` |
| `reports` | One row per CMA run | `id`, `access_code_id`, `status` (`running`, `succeeded`, `failed`), `subject` (JSON), `result` (JSON), `input_tokens`, `output_tokens`, `cache_read_tokens`, `cost_usd`, `created_at`, `finished_at` |

- Codes are stored as a hash and never in plain text. The operator sees the plain code once at issue time.
- **One active report per user** is enforced by the database: a partial unique index on `reports(access_code_id) WHERE status = 'running'`.
- Credit changes and report creation happen in a single database transaction, so a balance cannot go negative under concurrent requests.

## 4. Agent design

### 4.1 Division of responsibility

| Deterministic code (analysis engine) | Claude (agent) |
|---|---|
| Candidate search: radius, date window, size band, sub-type | Chooses the final 3–6 comps from scored candidates |
| Similarity scoring of candidates | Excludes outliers and states why |
| Dollar adjustments from a documented adjustment table | Decides whether to widen the search when candidates are thin |
| Adjusted values, value range and suggested list price | Writes the rationale and market narrative |

The model never produces a dollar figure that the engine did not calculate. The final report cites engine outputs only.

### 4.2 Tools

| Tool | Input | Output |
|---|---|---|
| `search_comps` | subject facts, radius (mi), months back, size band (%), statuses | Scored candidate list (closed sales or active listings) |
| `compute_adjustments` | subject, list of selected `ListingKey`s | Adjustment grid per comp and adjusted values |
| `compute_price_range` | adjusted values and weights | Low / high value range and suggested list price |
| `submit_cma` | selected comps, excluded comps with reasons, rationale, range reference | Final structured result (strict schema) |

- Tools use `strict: true` schemas, and every input is validated before execution.
- **Adjustment table:** per-area configuration for living-area rate ($/sq ft difference), bedroom, bathroom, garage space, lot size, age (per decade), condition step, and market-time adjustment (% per month). The table is documented in the code and shown in the report appendix.

### 4.3 Loop controls

- Built on the Anthropic TypeScript SDK with a manual tool loop, so each step can be streamed to the browser and recorded.
- **Safeguards:** a maximum of 10 model turns per report and a per-report token ceiling. A run that exceeds either ends as `failed`, and the reserved credits are refunded.
- **Prompt caching** on the system prompt and tool definitions, which are identical on every turn.
- Effort and thinking settings are tuned during the build against a fixed set of test subjects. Starting point: `effort: "medium"`.
- Handles `refusal` and `max_tokens` stop reasons explicitly and ends the run with a clear message instead of retrying.
- Token usage and computed cost are recorded on every report row.

## 5. Screens (Release 1)

1. **Access** (`/`): product description, disclosures, and an access code field. A valid code sets an HTTP-only session cookie. Invalid attempts are rate-limited.
2. **New CMA** (`/cma/new`): address autocomplete over the sample dataset. Selecting an address pre-fills beds, baths, living area, lot size, year built, garage spaces and condition, all editable. Shows the credit balance ("N reports remaining").
3. **Run** (`/cma/[id]`): live progress feed of agent steps as they stream. On completion, the same page shows results.
4. **Results** (same page): subject summary, comps table, adjustment grid, value range and suggested list price, rationale, excluded comps with reasons, and a **Download PDF** button.
5. **PDF report:** cover page, subject, comps, adjustment grid, pricing recommendation, rationale, methodology appendix (adjustment table), and disclosures on every page.

Every screen and every PDF page shows: "Sample data, not real listings" and "For demonstration only; not an appraisal or professional advice."

## 6. Credits

- New codes receive 45 credits by default. The operator can set any amount at issue time and grant more later (Release 1: through an operator command-line script that generates a code, stores its hash, and prints the plain code once).
- Starting a report reserves 5 credits. If the run fails for a system reason (model error, timeout, safeguard limit), the 5 credits are refunded through a `refund` ledger entry.
- A report cannot start if the balance is below 5 or if a report is already running for that code.
- The UI shows the balance in reports ("3 reports remaining"). Chat credits appear in Release 2.

### 7.3 Monthly budget (target under $50)

| Item | Estimate |
|---|---|
| Claude API | Bounded by issued credits; at the measured $0.0563/report average, the existing $40/mo Anthropic Console limit (set in Step 11) covers ~700 reports — no change needed |
| Vercel | $0 (Hobby); Pro ($20/month) when Hobby limits are reached; see C1 |

| Email (Release 2, Resend free tier) | $0 |

- **Provider safeguard:** a monthly spend limit configured in the Anthropic Console, set at or below the API budget.
- **Operator rule:** the sum of outstanding credits × cost per credit stays within the monthly API budget. At $0.0563/report (7.2) and 5 credits/report, a code issued with the existing 45-credit default represents ~$0.51 of real spend across its 9 reports — the default needs no adjustment from measured data.

## 8. Security and privacy

- Secrets (`ANTHROPIC_API_KEY`, `DATABASE_URL`, session secret) are stored in environment variables, never in code. A `.env.example` lists the names.
- Access codes are random, high-entropy, stored hashed, revocable, and checked with rate limiting.
- **Session length (updated by the operator-dashboard feature):** the session cookie's expiry changed from a fixed 30 days to a ~90-minute idle timeout (resets on activity, manual logout also available). See [operator-dashboard/spec.md](operator-dashboard/spec.md) for the mechanism (`proxy.ts`) and rationale.
- All database reads and writes go through server route handlers. The database is not exposed to the browser, and the application connects with a role limited to the tables it needs.
- User input to the model is limited to structured property facts with validated types and ranges. No free text in Release 1, which limits prompt-injection surface.
- No personal data is collected in Release 1 beyond the operator's label on each code.

## 9. Acceptance criteria (Release 1)

| # | Requirement | Verified by |
|---|---|---|
| A1 | Sample dataset loads with ~1,500 RESO-named records across 10 areas, reproducibly | Generator test: same seed produces identical output; counts per area and status within targets |
| A2 | Every area yields at least 5 closed comps for a typical subject with default search criteria | Automated test over one typical subject per area |
| A3 | Analysis engine adjustments match the documented table | Unit tests with hand-calculated expected values |
| A4 | Agent completes a CMA end to end and returns a valid `submit_cma` result | Integration test against fixed subjects (live API, run on demand) |
| A5 | Final figures in the result equal engine outputs | Test compares report figures to engine calculations |
| A6 | Progress events stream to the browser during a run | Browser check: steps appear before completion |
| A7 | PDF downloads and contains all sections and disclosures on every page | Automated PDF text check plus visual review |
| A8 | Starting a report deducts 5 credits; a failed run refunds them | Unit and integration tests on the credits service |
| A9 | A second concurrent report for the same code is rejected | Test of the database constraint and API response |
| A10 | A report cannot start with fewer than 5 credits; revoked codes are rejected | Tests on the credits service and access check |
| A11 | Runaway protection ends a run at the turn or token ceiling | Test with a stubbed model that never finishes |
| A12 | A new user understands the product within one minute | Manual review with at least two people unfamiliar with it |
| A13 | Disclosures appear on every screen and PDF page | Automated check plus visual review |
| A14 | Token usage and cost are recorded for every report | Test on report completion |
| A15 | `/api/health` returns 200 when the application and database respond, and an error status when the database is unreachable | Route test with the database available and unavailable |
| A16 | The automated test suite passes against a standard Postgres instance, not only Neon | Test run against a local Postgres database |
| A17 | The production build runs outside Vercel with only environment variables configured | `next build` and `next start` run locally against the test database |

A single `npm test` command runs all automated checks except live-API tests (A4), which run separately with `npm run test:live` because they incur cost.

## 10. Release 2 outline

To be specified in detail before the Release 2 build.

- **Request Access:** public form (name, email, company, role, reason). Submissions are stored and emailed to `khoa@nguyendesignlabs.com` through Resend.
- **Approval:** an operator-only admin page lists requests. Approving sets the credit allocation (default 45) and sends a sign-in email.
- **Accounts:** email magic-link sign-in using Better Auth, with users stored in the project's own Postgres tables. Release 1 access codes are migrated to, or coexist with, accounts.
